# 6f セッションの計測と結論（2026-10-31 16:00〜17:30 JST）

Claude Code のセッション 6f が、d8 セッションと分担して進めた SQL の改善と、その途中で分かったことの記録。
数値はすべて CI ベンチの計測欄（pg_stat_statements、alp、vmstat）と、サーバからの読み取り専用の確認による。

## 1. 分担

| セッション | 範囲 |
|---|---|
| d8 | DB 側（索引・pg_prewarm・設定）、JPEG 検証、実験枠 |
| 6f | Go 側の SQL の書き換え（Memories・FoF・友達申請・検索・RealMoji とコメントのロック・往復の削減） |

PR ごとの `/bench` は列が混むのでやめ、マージ前に本番データで新旧の SQL の出力（全列・並び順の md5）を比べてからマージし、まとめて main で測った。

## 4. 分かったこと

1. **PR のベンチが DB に作った物は、main の initialize では消えない。** close 済みの #225 が作った users のトリガー 3 本と `cache_versions` 表が残り、users への書き込みが 1 行の更新で順番待ちになって、main のベンチで DB 時間の 1 位（`UPDATE cache_versions` 1,690 回・平均 62.7ms・合計 106 秒）になった。#249 で片付けた。main のベンチの pg_stat_statements に main に無い SQL が出たら、残骸を疑う。
2. **asia2 のメモリはベンチ中に底に当たる。** #187 の前は available が 2.1GB → 約 85MB（ベンチ開始から約 45 秒）。バックエンド 1 本あたり約 14MB の私有メモリと PageTables 288MB が主。#187（asia のプール 80 → 64、文キャッシュ 64）の後は底が約 240MB。
3. **PgBouncer（#248）の後、DB は律速ではなくなった。** main bf92d5c（171,786）で DB の待ちのサンプルは前の約 1/4、asia2 の idle は平均 54%。代わりに asia1 のアプリのプール（64）の空き待ちが 1 回のベンチで 33,058 回・合計 3h58m、asia の `POST /api/posts` が平均 4.27 秒。asia1 は 99 秒中 43 秒で CPU が張り付いていた。
4. **閲覧可否の判定 `isureal_post_access` の中の文は軽い**（1 文 0.01〜0.08ms、4〜11 ページ）。関数全体の 20〜29ms は、文の実行の外（ロックの取得・計画の確認・CPU の順番待ち）にある。
5. **EU/US のプールは満杯だった**（europe1 の journal: `wait=11338 waitdur=34m49s`）。往復の数はすでにほぼ 1 回で、残る遅さはプール待ち。#195（EU/US 40 → 48）につながった。

## 5. 本番での確認のやり方（再利用できる）

- asia1 から psql を `PGOPTIONS="-c default_transaction_read_only=on -c statement_timeout=3s"` で使い、旧 SQL と新 SQL を `PREPARE` / `EXECUTE` で同じ引数に流して、出力全体の md5 と件数を比べる。署名鍵が出力に含まれるので、md5 は asia1 の上で取り、手元には件数と一致の真偽だけを持ってくる。
- 開いている投稿期間はベンチのたびに作り直されて消えるので、`w.ended_at IS NULL` を過去の日に置き換える（新旧の両方に同じように）。
- ベンチ中（asia2 のロードアベレージが高いとき）は確認を控える。pg_stat_statements は先に実行された文面を記録するので、確認の `PREPARE old ...` がベンチの計測に混ざることがある。
