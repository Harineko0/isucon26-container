## 2. 効いたこと（仕組みと PR）

| 変更 | 仕組み | 効果 | PR |
|---|---|---|---|
| 先に測る | `pg_stat_statements`、DB の wait event、nginx の apptime を毎ベンチ CI の「計測」欄に出す | 推測ではなく最も重い所から順に手を付けられた | #87 |
| 画像 INSERT をロックの前へ + `STORAGE EXTERNAL` | TOAST 書き込みを行ロックの外に出し、圧縮を省く | 投稿のクリティカルセクションが短くなる | #62 / #85 系 |
| サーバごとの create_post ゲート | 画像 INSERT の同時実行数を絞り、DB のロック待ちをアプリ側の待ちに置き換える | 画像 INSERT 平均 390 → 72〜88 ms、create_post 380 → 約 100 ms | #107 |
| `posted_at` を DB で決める | 関数内で DB 時計から決め、投稿期間との境界判定をアプリの時計に依存させない | 409 が消えた | #72 → #85 |
| 投稿期間の開始を 2 トランザクションに + 通知 INSERT を非同期に | 応答を先に返し、notifications の大量 INSERT を後ろに回す | asia の投稿期間開始が 8 秒遅れていたのを解消 | #107、#115 |
| フィード SQL をフィード種別ごとに 1 文 | 共通の巨大クエリをやめ、開いている期間の投稿を先に出す。閲覧者 103 人で旧実装と不一致 0 を確認 | フィードの DB 時間を削減 | #103 |
| ユーザー検索を trigram 候補に | 全ユーザーをソートする代わりに GIN trigram で候補を絞る | 検索が DB 時間の 26% を占めていたのが消えた | #96 |
| EU/US の経路を DB 1 往復に | SSE/投稿期間（#64）、プール: idle ping なし・TLS なし（#85）、書き込み（#110）、GET（#120）でセッション確認を本処理と同じ 1 文に | 1 要求 ≈ 遅延 1 回分（0.1 s）が下限になった | #64、#85、#110、#120 |
| JPEG 検証を画素復元なしに | ヘッダと Huffman 構造だけ検証する | 1 枚 約 43 → 約 22 ms、asia1 の CPU が上限でなくなった | #70（#85 に統合） |
| アップロードのバッファを事前確保 | 受信サイズに合わせて確保し、再割り当てを減らす | GC と allocation の削減 | #107 |
| initialize の修正 | 初期データのプロフィール画像を残す（#105）、`created_at` の BRIN で削除を速く（#108） | FAIL 要因の除去と初期化時間の短縮 | #105、#108 |
| DB ログから画像の hex を出さない | slow-log の bind パラメータを 64 バイトで切る | asia2 のログ I/O が消えた | #63 |
| PostgreSQL の bgwriter / WAL writer | backend より先に書き出させ、checkpoint 間隔を 2.2 → 4.3 GB に | 投稿期間開始時の書き込みスパイクを平準化 | #104 |
| 画像を DB の外へ | 受け付けたリージョンのディスクに本体、DB にはメタデータ | TOAST ロック・WAL の約 45%・リージョン間アップロードがクリティカルセクションから消えた。単独ベンチ 77,098 | #128（チーム担当） |

## 3. 効かなかったこと・教訓

| 事象 | 何が起きたか | 教訓 |
|---|---|---|
| pg_prewarm | `shared_preload_libraries` は再起動が要る設定で、`infra/deploy.sh` が reload しかしないため以後のベンチが全部デプロイ失敗（#86 → #91 で戻す） | reload で効く設定だけを deploy に入れる。再起動が要るものは人の手による PostgreSQL 再起動とセットにする |
| ゲート 12 | 8 より悪化（GP 19/374、タイムアウト 20、#116/#118 → #121 で戻す） | 投稿はどちらにせよゲートで並ぶ。レバーは同時実行数ではなく投稿 1 件あたりのコスト |
| notifications の削除 `IN (SELECT …)` | ANALYZE 後も seq scan のまま | `= ANY(ARRAY(…))` なら 9.5 ms（検証済み、未マージ） |
| ベンチのばらつき | 同じツリーで 63,766 と 66,429 | 1 本では 5% 未満の差は判定できない。小さい変更は束ねて測る |
| PR ごとのベンチ | キューが 10 本以上に。古い run はキャンセル、main のベンチは手動のみに（#113） | ベンチはチームで同時 1 本。単位ごとに測るより、まとめてマージしてから測るほうが早い |
| Windows の罠 | `/c/...` が `C:\c\...` になる、作業コピーが CRLF、`go build -o /dev/null` が複数パッケージで失敗 | worktree は `git worktree list` で実パスを確認。CRLF は `.gitattributes` で固定 |
| `pipefail` 無しのシェル連鎖 | サイズ期待値のテストが失敗していたのにマージが通った | CI のシェルは `set -o pipefail` を必ず付ける |
| ガード hook | 読み取り専用の psql も止める | 同値確認はファイル経由の読み取り専用セッションで実行した。hook の判定を「書き込みを含むか」に寄せる |
| submodule → monorepo | 昼に切り替え（#74）、進行中のブランチを載せ直す必要があった | リポジトリの形は開始前に決める |

## 4. 持ち越し

- notifications の削除を `= ANY(ARRAY(…))` に（検証済み 9.5 ms、未マージ）。
- `user_search_norms` の孤児行 約 10k 件の掃除。
- 残っている 2 往復の書き込み: PATCH/DELETE posts、DELETE comments/realmojis。
- `wal_buffers` と pg_prewarm は、人の手による PostgreSQL 再起動とセットで入れる。
- 再起動リハーサル（[final-runbook.md](final-runbook.md) §1）は実施できなかった。追試は冷えた状態で最終スコアの 75% 以上が要る。
- 次の構成は、画像を DB の外に出したうえでの同期リージョンレプリカ（[architecture-review.md](architecture-review.md) §3-2）。
- 凍結後マージの #134（画像署名の exp バケット 30 秒、users の外部キー削除）はマージ後にしかベンチしていない。
