# Claude がやったこと

作業した 3 つのセッション（d8、container-be、6f）について、出した PR、判断、失敗をまとめる。
時刻は JST、スコアは CI のベンチの結果である。

## d8

d8 は 10:18 から 17:43 まで動いたメインのセッションである。
役割は、環境の把握、issue の起票、計測、PR を作ってマージするループ、終盤の判断と移っていった。

### 現状の把握（10:18〜11:56）

d8 は最初の 1 時間半を、サーバーに何も変更を加えずに現状を測ることに使った。
CloudWatch、`ping`、psql の `SELECT 1` で、EU/US から DB への往復が 100ms あること、EU/US のサーバーの CPU が 4% 以下で待ちに時間を使っていることを確かめた。
そのうえで、取り組む問題を「EU/US で、投稿からフィード確認までの SQL の往復を減らす」の 1 つに絞って提案した。

ところが 11:44 に、チームの誰かが 3 台へ未コミットの大きな変更を配っていた。
d8 はその版のコードを読み、主要な API がすでに 1〜2 往復まで減っていることを確かめて、自分の提案の伸びしろは小さいと報告した。

ユーザーから「DB をレプリケーションして europe などに置く」案を聞かれたときは、次の理由で見送りを勧めた。

- 非同期のレプリケーションは、書き込みの後の読み取りに古い値を返し、ブロックした相手の投稿がフィードに出るといった FAIL を起こす。
- 同期のレプリケーション（`synchronous_commit = remote_apply`）なら仕様は守れるが、書き込みが 1 回あたり 0.2 秒以上かかる見込みになる。
- 「通信遅延を回避すること」の禁止に当たるかどうかが、マニュアルからは判断できない。

### issue の起票（12:05〜12:43）

d8 はサブエージェント 5 本に、DB とログイン、画像、フィードと投稿、通知と投稿期間、運用と初期化を分担させて改善点を洗い出した。
候補 51 件のうち、チームがすでに起票していた #13〜#22 と重なる 18 件を除き、33 件（#23〜#55）を起票した。
内訳は P0 が 4 件、P1 が 8 件、P2 が 21 件である。
P0 には、初期データの画像が消える疑い（#25）、全ユーザーを走査するユーザー検索（#26）、全台再起動のリハーサル（#24）が入っていた。

### DB が律速だと特定する（13:54〜14:22）

d8 はベンチ中の `vmstat` と `pg_stat_statements` から、DB（asia2）の CPU がほぼ 100% に張り付き、DB 時間の 40% をユーザー検索、35% を投稿作成が使っていると特定した。
これを issue #97 にまとめ、接続プールの満杯（#68）は DB の CPU 飽和の結果である可能性が高いと書いた。

ユーザーの依頼で、検索を補う #106 をサブエージェントに作らせた。
検索用の補助テーブルが、削除済みユーザーの行でベンチ 1 回ごとに約 900 行ずつ膨らんでいたので、initialize で消すようにしたものである。
あわせて okdaichi さんの #96（検索の書き直し）を検証し、68,232 点（main 比 +25.9%）と、検索 1 回が 498ms から 66ms になったことを確かめた。

- 実測から狙いを決めて、PR をサブエージェントに並列で作らせる。
- ベンチの前に必ず `origin/main` を取り込む。
- 15:08 の方針変更の後は、PR ごとのベンチをやめ、差分を読んで問題がなければマージし、効く変更が入ったときだけ main をベンチする。

### 「最強の状態」の実験と、その残骸（16:15〜16:57）

16:15 に「40 万点級が要る」と言われ、d8 は Fable のサブエージェント 1 本に実験 PR を作らせた。
設計は、読み取りに要るデータを各リージョンのアプリのメモリに持ち、書き込みは DB に確定させた後、応答の前に他の 2 リージョンへ同期で反映するものである。
60 分で全部は作れないので、範囲をユーザー検索だけに絞った #225 が出た。

#225 のベンチは 97,727 点で、main（96,527 点）とほぼ同じだったので close した。
しかし #225 のベンチは、DB にトリガー、関数、表を作ったまま残していた。
main の initialize はそれを消さないので、16:46 の main のベンチで、users への書き込みがそのトリガーの 1 行の更新で順番待ちになり、DB 時間の 1 位（106 秒）になった。
d8 は 16:50 に、残骸を initialize で消す #249 をマージした。
16:57 の main は、チームの PgBouncer（#248、#254）と #249 が入って 171,786 点になった。

16:48 に「最強の状態を一発で」と言われたとき、d8 は「検証済みでまとめて載せられる PR はなく、今の main に #249 を足した状態が最強」と返した。
開いている PR はどれもベンチされておらず、大きな作り直しを 17:30 までに検証する時間もなかったからである。

### 終盤（17:11〜17:43）

17:11 に d8 は、今日中に 40 万点には届かないとユーザーに伝えた。
171,786 点から 40 万点には 2.3 倍以上が要るが、残る最大の取りこぼし（asia のグランプリ、995 人中 246 人）を全部取っても約 1.5 万点にしかならないからである。

17:13 にユーザーから Codex を使ってよいと言われ、Orca から起動したが、利用上限で使えなかった。
d8 は自分で asia1 のプロファイルを取り、画像 URL の署名が CPU の約 33%（そのうち Memories が 28%）を使っていると分かった。
署名の期限を 30 秒単位で丸めていたので、約 100 秒のベンチの中で同じ画像の署名を 3〜4 回作り直していた。
そこで丸めを 300 秒にする #277 を 17:17 にマージした。

17:23 の main のベンチは「初期データの検証に失敗しました」で FAIL した。
d8 は 17:25 に #278 で revert し、17:28 に 168,143 点で PASS することを確かめた。
期限の丸めは今日一日 30 秒で通っていたので、ベンチャーが発行された期限を厳しい幅で確かめていた可能性がある（原因の詳細は確かめていない）。

17:30 以降、ユーザーから「もっと PR を出して」と言われたが、d8 は出さなかった。
17:30 で PR のベンチが締め切られ、新しい変更は main に入れて測るしかなく、最終スコアは最後のベンチなので、FAIL すれば記録を失うからである。
17:32 に Memories の署名を詳しく見て、重複の除去と使い回しがすでにあり、削れる無駄がないことも確かめた。
17:43 の「stg を作ってベンチして」という依頼にも、「17:42 の main（202,017 点）で止めるべき」と返した。

## container-be

container-be は 12:20 から 17:11 まで動いた。
前半は issue を担当して PR を出し、14:52 からは PR の見張り役に回った。

### issue の担当（12:20〜14:38）

最初に #14（EU/US の初期画像のキャッシュ）を担当した。
ユーザーの許可を得て app の main へスナップショットを直接 push し、画像の一括コピーを流した。
このコピーが DB から約 20GB を読み、12:41 のベンチ（41,587 点）に影響した可能性が高い。
asia2 はメモリが 4GB しかないので、DB のよく使うデータがページキャッシュから追い出されていたと見られる。
12:54 からは、変更をすべて container リポジトリへの PR で出すやり方に切り替えた。

13:12 からは、worktree ごとにサブエージェントを並列で動かした。

|---|---|---|---|
| #61 | #14 | 画像コピーの再開対応と枚数の確認 | 13:04 マージ |
| #67 | #25 | プロフィール画像の変更で初期データの画像の行を消さない（予防の修正） | 45,874 点、13:38 close |
| #69 | #31 | DB から取った初期データの画像をディスクに書き戻す | 52,084 点、14:16 マージ |

| #89 | #51 | 友達関係の関数の行ロックを 2 人組の advisory lock に替える | 54,717 点、14:17 マージ |

#21（索引の追加）は、対象の SQL が DB 時間の 0.05% 未満だったので見送った。

この時期の分析で効いたのは、13:48 と 14:08 の 2 つである。
asia のグランプリが 205 人中 8 人しか取れていない原因を、投稿期間の開始時に約 200 人が一斉に投稿して DB の CPU を使い切ることだと特定した。
さらに、okdaichi さんの #90 で asia のプールを 40→80 本にすると、asia のグランプリは 8→168 人に増えたが、EU/US は 33 人と 32 人に落ちたことに気付いた。
DB の処理能力を asia と EU/US で奪い合っているだけなので、全体を伸ばすには DB の仕事そのものを減らす変更（#96 の検索と #80 の画像）が要る、という結論である。

### PR の見張り（14:52〜17:11）

14:52 からは、ユーザーの指示で、点を落とす PR を close するループを回した。
判定は毎回同じスクリプトで行い、条件は次のとおりである。

- ベンチが FAIL した。
- スコアが直近の main 3 回の中央値より 10% 以上低く、かつ 3 回の最低値も下回った。
- 耐久性を下げる設定を足した。

close するときは、ジョブ番号、スコア、main との比較を日本語でコメントし、「reopen して `/bench` すれば再評価する」と添えた。

| PR | 理由 | その後 |
|---|---|---|
| #186 | 81,185 点、main 比 -13% | |
| #184 | 60,867 点、main 比 -35%、initialize が 10.2 秒 | 直そうとしていた不具合（エクスポートの map の並行書き込み）は、コメントで勧めた mutex の形で #255 として出し直された |
| #261 | 新しいコミットがユーザー登録の 500 で FAIL | 作者が直して 186,774 点で PASS し、17:25 にマージされた |

ほかに、新しく開いた PR ごとに仕様上の危険を注記した。
#188 はブロックとコメントの競合の順序に関わること、#199 は主催者の BAN 処理が読む action log に関わること、#238 の `commit_delay` は耐久性を下げないことなどである。
16:52 には、#248 の PgBouncer で asia1 のアプリが起動しなくなる件を見つけ、main のベンチが FAIL するおそれを知らせた。

17:03 には、レギュレーション違反の点検を、基盤と耐久性、外部仕様、一貫性と initialize の 3 つに分けて Fable のサブエージェントで始めた。
しかし 17:06 に利用上限に達し、結果が出る前に止めた。

## サブエージェントの使い方

3 つのセッションは、合わせて 38 本のサブエージェント（d8 が 14 本、container-be と 6f が 12 本ずつ）を起動した。
どのセッションも、サブエージェントには専用の clone か worktree で作業させ、次の内容を書いたブリーフを渡した。

- 守るべき仕様上の条件と禁止事項
- その時点の実測値（main のスコア、ぶれの幅、DB 時間の内訳）
- 1 PR 1 テーマにすること、ベンチの前に `origin/main` を取り込むこと
- マージの判断は親のセッションが行うこと

午後からは、大きな変更や検証の重い作業に Fable を使った。
d8 の JPEG 検証の作り直し（#189）や「最強の状態」の実験、container-be のレギュレーションの点検がその例である。
