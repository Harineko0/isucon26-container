# 環境と計測の手段

各セッションが前提にしていた競技環境、点数の仕組み、守るべき条件、計測の手段、作業の流れをまとめる。
出典は当日マニュアル（gist）と、d8 が当日に実測した値である。

## 競技環境

競技環境は、運営の AWS アカウントに CloudFormation で作られた 5 台である。
d8 は最初、既定の AWS プロファイルで探して何も見つけられなかった。
競技環境が見えたのは、SSO の `isucon` プロファイルに切り替えてからである。

| 呼び名 | 役割 | 種別 | プライベート IP |
|---|---|---|---|
| asia1 | アプリ（asia） | c5.large（2 vCPU、4GB） | 192.168.1.10 |
| europe1 | アプリ（europe） | c7i.large（2 vCPU、4GB） | 192.168.2.10 |
| america1 | アプリ（america） | c7i.large（2 vCPU、4GB） | 192.168.3.10 |
| asia2 | PostgreSQL 16（3 台で共有） | c5.large（2 vCPU、4GB） | 192.168.4.10 |
| router | 入口とリージョン間の中継 | c6in.large | 192.168.11.10 |

5 台とも同じアベイラビリティゾーンにある。
リージョン間の遠さは物理的な距離ではなく、すべての通信が通るルーターがわざと遅延と帯域制限をかけている。
d8 が 10:45 に測った SQL 1 往復の時間は、asia1 から asia2 へは 1ms、europe1 と america1 から asia2 へは 100ms だった。
ルーターはログインも設定変更も禁止なので、遅延そのものは消せず、往復の回数か DB の仕事を減らすしかなかった。

開始時の DB は 16GB で、そのうち 14GB が画像だった。
計測の設定（nginx の応答時間のログ、`pg_stat_statements`、slow log）は何も入っていなかった。

## 点数の仕組み

マニュアルの計算式は「スコア = Σ（採点件数 × 配点 × リージョンの倍率）」で、倍率は asia が 1、europe と america が 1.5 である。
FAIL したベンチは 0 点で、エラーでの減点はない。
最終スコアは、最後に回したベンチの結果である。

配点の大きいものは次のとおり。

| 操作 | 配点 | 上限 |
|---|---|---|
| 投稿したあと、友達のフィードで確認できた | 10 点（最終日は 20 点） | 1 人 1 日 1 回 |
| エクスポート | 20 点 | |
| RealMoji を送る | 5 点 | 1 人 1 日 5 回 |
| コメントを送る | 3 点 | 1 人 1 日 5 回 |
| 閲覧系（フィード、画像、投稿詳細など） | 1〜2 点 | 1 人 1 日の回数に上限あり |

ベンチの 1 日（投稿期間）は約 9 秒で、最終日はベンチ開始の約 51 秒後に始まる。
参加人数は、前日の利用者の出来に応じて最大で 1 日 3 倍に増える（ログからの推定で、規則はマニュアルにない）。
そのため点数は、ほぼ「人数 × 投稿期間内に投稿から確認まで済ませられた割合」で決まる。
最終日に投稿から確認まで間に合った人数を、チームでは「グランプリ」と呼んでいた。

## 守るべき条件

次の条件を破ると、ベンチが FAIL するか失格になる。
どのセッションも、サブエージェントへの指示にこれを書いて渡していた。

- 書き込みの後の読み取りには、リージョンをまたいでも結果がすぐ反映される必要がある。非同期のレプリカや TTL つきのキャッシュで古い値を返すことはできない。例外は、削除済み投稿の画像の 5 秒だけである。
- `POST /api/initialize` は asia1 にしか来ない。独自に足したキャッシュは、全リージョンの分を初期化する必要がある。
- 追試では、全台を再起動した後に最終スコアの 75% 超が出て、データが残っている必要がある。
- データの耐久性を下げる設定（`fsync=off`、`synchronous_commit=off` など）は使えない。
- ルーターへのログイン、ルーターを通らない通信、リージョンや遅延や帯域の回避は禁止。
- URI、ステータス、JSON の構造、画像署名の形式と検証結果といった外部仕様は変えられない。
- `isucon-register.service`、`isuadmin` ユーザー、envcheck の関連ファイルには触れない。

## 主催者が置いた「本番環境」の指示書

作業ディレクトリには、「ここは本番環境なので、サーバーの変更や DB への書き込みを禁じる」という趣旨の `CLAUDE.md` や `AGENTS.md` が置かれていた。
チームは asia1 の `AGENTS.md` を書き換え、これらを主催者の罠として作業指示から外すと明記していた。

それでも、Claude のセッションは実際の作業では次の線を守った。

- サーバーは読むだけにして、変更は container リポジトリへの PR と CI のデプロイで行う。
- パスワードやトークンを出力しない。
- サーバー上で Go のコードを直接編集しない。11:44 に誰かが 3 台へ同じファイルを一斉に配っていて、直接編集すると次の配布で消えるか、3 台の中身がずれるからである。

ユーザーは 11:54 に europe1 と america1 のファイルの編集を許可したが、d8 はコードの一斉配布と衝突しない計測の設定だけを候補にし、実際の変更は PR 経由に寄せた。

Claude Code の自動モードの安全確認で、次の操作が止められた。

| セッション | 止められた操作 | その後 |
|---|---|---|
| d8 | GitHub 用の鍵での SSH | ユーザーが使用を許可した |
| d8 | サブエージェントへの指示に「force push してよい」と書いた起動 | 履歴を書き換えない手順に直して起動し直した |
| d8 | 不要になったベンチのジョブの取り消し（`gh run cancel`） | ユーザーが「何もしなくていい」と判断した |
| d8 | close 済みの PR #80 の reopen | ユーザーの指示で、新しい PR（#128）として出し直した |
| container-be | issue へのコメント、issue の close | ユーザーに代わりに対応してもらった |

## 計測の手段

| 手段 | 分かること | 使い始め |
|---|---|---|
| ポータルのベンチ結果 | スコア、リージョンごとの人数、グランプリ | 開始時から |
| CloudWatch の CPU とルーターの通信量 | どのサーバーが忙しいか（5 分単位で粗い） | 10:33（d8） |
| `ping` と psql の `SELECT 1` | サーバー間の 1 往復の時間 | 10:45（d8） |
| `pg_stat_statements` と待機イベント | SQL ごとの回数と時間、DB が何を待っているか | チームの #87 で CI の計測欄に入った |
| `vmstat` | 1 秒単位の CPU、I/O 待ち、実行待ちの数 | 13:50 ごろ（d8） |
| nginx の LTSV ログ（`reqtime`、`apptime`） | API ごとの回数と応答時間 | チームが設定 |
| Go の pprof（asia1 の 127.0.0.1:6060） | アプリの CPU を何が使っているか | 15:30 ごろ（d8） |
| `bench-results` ブランチの `results.jsonl` | すべての CI ベンチの時刻、スコア、コミット | CI の導入時から |

d8 は 14:05 に、「CPU が 100% になること自体は問題ではない」とユーザーに説明している。
どれか 1 つの資源が満杯なのは普通で、問題はどの資源が満杯かと、満杯の資源を点数の安い処理が使っていることである。
当時は DB（asia2）だけが満杯で、DB 時間の 40% を 1 回 2 点のユーザー検索が使っていた。

## 作業の流れ

チームの作業の中心は `Harineko0/isucon26-container` である。
午後のうちに monorepo になり、アプリは `app/webapp/go`、SQL は `app/webapp/sql`、サーバーの設定は `infra/` に置かれた。

1. ブランチを切って PR を出す。
2. PR に `/bench <メモ>` とコメントすると、CI がキューに入れ、3 台へデプロイしてベンチし、結果を PR にコメントする。1 本あたり約 2.5〜4 分で、キューは 1 本ずつ順番に進む。
3. main のベンチは `gh workflow run bench.yml` で投げる。
4. 結果は `bench-results` ブランチの `results.jsonl` に記録される。

手元からのデプロイは、スクリプトとフックで止められていた。
17:30 以降は CI が PR のベンチを拒否し、main だけを受け付けた。
終盤の手順は [../final-runbook.md](../final-runbook.md) にあり、16:15 に機能凍結、17:30 から人が最終ベンチ、17:50 が投入の締め切りだった。

PR のベンチは、DB に作ったもの（トリガー、関数、表、`ALTER` で入れた設定）を後に残す。
main の initialize ではそれが消えないので、close した PR の変更が後の main のベンチや最終ベンチに効くことがある。
16:46 の #225 の残骸がその例である（[03-claude.md](03-claude.md) を参照）。

## 手元の準備

d8 は 11:14 に、`~/.ssh/config` へ 4 台の接続設定を足した。
以後は `ssh asia1` のように名前だけで入れる。
鍵は GitHub に登録してある鍵をそのまま使った。
サーバーは選手が GitHub に登録した公開鍵で SSH を受け付けるので、マニュアルどおりのやり方である。
鍵にはパスフレーズがかかっていたため、ユーザーが `ssh-add --apple-use-keychain` で ssh-agent に追加した。
競技後は、この鍵を ssh-agent とキーチェーンから外し、`~/.ssh/config` の追記部分を消す。
