## 効いた判断

### 役割をセッションごとに分けたこと

ユーザーは、d8 に PR を作ってマージするループ、container-be に PR の見張り、6f に d8 が見ていない Go 側の SQL を任せた。
6f は開始直後に、同じループを 2 つ回すとマージやベンチの列が衝突すると指摘していた。
15:40 に担当を分けたことで、16 時台に d8 と 6f が並行してマージしても、同じファイルや同じ PR を取り合うことはなかった。

### 自律ループを任せたこと

14:44 にマージの判断までを任せてから、d8 は 15:04〜16:19 の 75 分で 9 本をマージした。
それ以前は、PR ができるたびにユーザーの判断を待っていて、container-be では #69、#71、#89 がマージ待ちのまま積み上がっていた。

### PR ごとのベンチをやめたこと

15:08 の時点で、CI のキューにはチーム全体の PR のベンチが何本も並んでいた。
PR ごとのベンチをやめ、大きな変更の後だけ main をベンチするようにしたことで、効いた変更の効果を main で早く確かめられるようになった。
その代わり、16 時台にマージした PR の多くは単独では測られておらず、どれがどれだけ効いたかは切り分けにくくなった。

### 「壊さないこと」を念押ししたこと

17:40 にユーザーは、6f に「今は壊さないことが大事」と念を押した。
最終スコアは最後のベンチで、FAIL すれば記録がなくなる。
6f はこれを受けて、締め切り後の PR をマージもベンチもせずに出すだけにした。

## 難しかった判断

### 40 万点という目標と機能凍結

チームの手順書では 16:15 が機能凍結だったが、同じ 16:15 にユーザーは「40 万点級が要る」として大きな実験を求めた。
d8 は 16:47 に「もうマージもベンチの投入もしない」と宣言したが、その後も続いた依頼に応えて #277 をマージし、17:23 の main を FAIL させた。
「最強の状態」の実験（#225）も、スコアは伸びず、DB に残骸を残して 16:46 の main を遅くした。

17:11 に d8 が示した見積もりでは、171,786 点から 40 万点には 2.3 倍以上が要り、残る最大の取りこぼしを全部取っても約 1.5 万点だった。
この見積もりより前に目標と残り時間の折り合いをつけていれば、終盤の 2 つの失敗は避けられた可能性がある。

### 同じ依頼を 2 つのセッションに出したこと

17:43 に d8、17:45 に 6f へ、stg を作ってベンチする依頼が出た。
d8 は止めることを勧めて返事待ちになり、6f は #303 を作ってベンチした。
結果として #303 は PASS し、害はなかった。
ただ、片方が止めるべきだと判断した操作を、もう片方が実行した形になっている。
最終スコアに関わる操作は、どのセッションが担当するかを 1 つに決めておくと、判断が食い違ったときに気付きやすい。

### main への直接 push

12:30 に container-be へ main への直接 push を許可したことで、Harineko0 さんの PR と 6 ファイルで衝突した（Harineko0 さんが 12:55 に解消した）。
24 分後の 12:54 には、PR で出すやり方に切り替えている。
