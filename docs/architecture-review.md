## 2. 上限はどこにあるか（計測）

| 層 | 計測値 | 判断 |
|---|---|---|
| ルーター | ベンチ中でも asia1→asia2 0.98 ms、EU/US→asia2 100.9 ms・ジッタ 0.05 ms・損失 0 | 容量の上限ではない。上限はルールとしての遅延と帯域制限 |

| EU/US の 1 要求 | DB 往復 1 回 ≈ 0.1 s（負荷中 0.2 s）。ほぼ全 API が 1 往復になった（#64 #85 #110 #120） | 下限は設定された遅延。これ以下にはローカルのデータでしか行けない |
| EU/US のアップロード | 投稿 1 件 360 KB が帯域制限の回線を DB 呼び出しの中で通る | 期間開始時は帯域で律速 |

## 3. 次の構成（効果 ÷ リスクの順）

1. **画像を DB の外へ**（#33、実装済み、単独ベンチで +9%）。受け付けたリージョンのディスクに本体、DB にはメタデータ。
   他リージョンからはルーター経由の内部経路で取りに行く。TOAST のロック、WAL の約 45%、リージョン間アップロードが
   クリティカルセクションから消える。どのリージョンからも同じ画像、削除後 5 秒で 403、は DB 側の判定で維持できる。
2. **リージョンごとの同期レプリカで読みをローカルに**（PLAN.md の案 C）。europe1/america1 に PostgreSQL のレプリカ、
   `synchronous_commit = remote_apply`。読みは 0 ms、書き込みは最も遠いリージョンの往復分遅くなる。read-after-write は
   コミットが適用を待つので守られる。**1 の後でしか成立しない**（画像入りの WAL が帯域制限の回線を流れるため）。
   EU/US を何倍にもできる唯一の変更だが、数時間の作業と追試のリスクがある。
3. **残っている 2 往復の書き込み**（PATCH/DELETE posts、DELETE comments/realmojis、約 100 回/走行）と、
   `user_search_norms` の孤児行（live の約 3 倍）の掃除。小さく安全。
4. **投稿の受け付け**: 1 が入ればゲートは不要になる。それまでは DB のロック待ちをアプリ側の待ちに置き換えているだけで、
   asia は 8 が 12 より良かった（グランプリ 125/400 対 19/374、タイムアウト 0 対 20）。

## 4. ルールすれすれの手は採らない

画像署名の `exp` の丸め幅を広げれば署名の再計算は大きく減るが、「期限の形式と検証結果を変えない」に抵触しうる。
耐久性を下げる設定は失格。どちらも FAIL に見合わない。
