# ISUCONの性能改善

サービス全体の正しさを維持し、評価対象の負荷で処理量と応答時間を改善する。特定のミドルウェアや得意な技術から着手せず、現在の律速要因から次の変更を選ぶ。

出典と読書範囲は [references/source-coverage.md](references/source-coverage.md) を参照。本に載った数値・設定・改善順を、対象環境で検証された事実として扱わない。

## まず評価の契約を確認する

- 競技の規約、採点式、正当性チェック、初期化処理、永続化、許可されたサーバーと外部サービスを確認する。まだ不明な条件は明示する。
- クライアントからリバースプロキシ、アプリ、DB、キャッシュ、外部APIまでの処理経路と、それぞれの配置・プロセス数・接続先を把握する。
- ベンチマークの実行方法、対象URL、計測時間、並列度、データ量、キャッシュ状態、ビルド・再起動方法を確認する。既存の変更を巻き戻さず、変更前の状態を識別できるようにする。

## 計測から改善する

1. **比較可能な基準を作る。** 変更前に正当性と性能を測る。実行時刻、対象の版、設定、初期データ、与負荷条件、スコア、エラー、応答時間、処理量を同じ試行に紐づけて残す。初期化、ウォームアップ、計測区間を混同しない。
2. **外側から絞り込む。** 負荷中に、与負荷側と被負荷側のCPU・メモリ・ディスクI/O・ネットワークを観察する。入口から各構成要素の入出力と待ち時間を比較し、詰まりが発生している層を特定する。使用率が高いだけで原因と断定しない。
3. **原因を示す証拠を得る。** 遅い経路の内側をログ、クエリ解析、トレース、プロファイル等で掘り下げる。総時間、実行回数、1回のコスト、転送量、待ちを区別し、どの処理を減らすと全体に効くか説明する。
4. **仮説を一つ試す。** 観測事実、原因仮説、変更、期待するメトリクスの変化、正しさへの影響を短く示してから実装する。原則として効果を切り分けられる単位で変更する。時間制約で複数の変更をまとめる場合、個々の効果が未分離であることを記録する。
5. **同条件で判定する。** 正当性チェックとベンチを再実行し、スコアだけでなくエラー、応答時間、処理量、リソース消費を比較する。小さな差や変動がある場合は複数回測り、都合のよい1回だけを選ばない。効果がなければ仮説を更新し、その変更を残す理由を再検討する。
6. **次の律速要因を探す。** 改善済みの箇所を磨き続けず、全体を再計測する。目標・残り時間・利用可能な資源を踏まえて次の一手を選ぶ。

処理そのものや呼び出し回数を減らす方法を先に検討する。アルゴリズムやデータアクセスの問題を、無制限な並列化・接続数増加・タイムアウト延長だけで覆い隠さない。キャッシュや配置変更も、その必要性と整合性を検証した上で選ぶ。

負荷生成機のCPU、FD、接続数、ネットワークが先に限界に達していないか確認する。単一URLへの簡易試験の結果を、そのままログイン・書き込み・画像取得を含む競技全体の性能に一般化しない。

採用する変更は初期化後・キャッシュが空の状態・再起動後にも成立させる。適用した設定が実際のプロセスで有効か確認し、最終計測では調査用の詳細ログや計装の負荷も揃える。

結果は「変更」「観測された効果」「正当性の確認」「次のボトルネック」「未検証事項」を簡潔に報告する。実行できなかったベンチ、再起動、実環境確認を、成功したと表現しない。
