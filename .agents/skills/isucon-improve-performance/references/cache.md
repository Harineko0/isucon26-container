# キャッシュを導入する判断と検証

## 導入前に決める

まずクエリ・取得範囲・呼び出し回数を改善する。生成コストと再利用頻度から、キャッシュの通信・直列化・メモリ・運用コストを上回る効果があるか判断する。

- 正本、キー、値の形式と版、容量上限、TTL、更新・削除経路、許容できる古さを定義する。TTLだけで更新直後の整合性が保証されると考えない。
- ユーザー・権限・対象種別を混同しないキーを使う。同じ値の無意味なキー増殖を避ける。形式変更時に旧データを読めるか、世代を切り替えるかを決める。
- プロセス内キャッシュは共有範囲とロックが必要。複数プロセス・複数台で値が分かれ、再起動で消える。二層構成は各層のTTLが古さを延ばす点も確認する。
- 共有KVSはネットワーク往復と新たな障害点を増やす。Redis等の重いコマンドや長い処理が他の要求を止めないか調べる。永続性が必要な正本を、消えてよいキャッシュと混同しない。

## 更新方式を選ぶ

| 方式 | 向く状況 | 必須の確認 |
| --- | --- | --- |
| ミス時に同期生成 | 必要なデータだけを生成したい | 初回の遅延、同時ミスの集中、更新と生成の競合 |
| 古い値を返して非同期更新 | 古さを仕様上許容できる | 古さの上限、初回に返せる値、更新失敗、重複生成の抑止 |
| 定期生成 | 対象集合が限定できる集計等 | 無駄な生成、更新遅延、ジョブ停止、キャッシュ消失後の復旧 |

同じキーの同時生成はsingleflight等でまとめる。ただしプロセス内の抑止が複数台にも効くとは限らない。必要なら共有層での制御を検討する。全キー共通ロックで無関係な要求まで直列化しない。期限の分散・早期更新も、集中の証拠と許容する古さに基づいて選ぶ。

更新・削除は、DBトランザクションの成功・失敗や並行読み取りとの順序まで確認する。単に「書き込み後に削除」を追加して全競合が解決したと扱わない。初期化時には派生データも確実にリセットする。

## 効果と正しさを確認する

- ヒット率は計測区間の差分から求め、要求数・キー別の偏り・生成時間・KVS往復時間と合わせて見る。ヒット率だけを目的にしない。
- eviction、容量、タイムアウト、接続数、再生成回数、正本の負荷を観測する。memcachedのget_hits/get_misses/evictions、Redisのkeyspace_hits/keyspace_misses/evicted_keys等を使えるか確認する。
- 空・温まった状態、期限切れ集中、更新直後、削除、別ユーザー、並行生成、再起動、KVS障害で検証する。障害時に正本へ要求が集中する設計なら、その負荷も試験する。
- 不適切なデフォルト値や古い値を返して高速化したことにしない。競技の正当性条件を満たす方式だけを採用する。
