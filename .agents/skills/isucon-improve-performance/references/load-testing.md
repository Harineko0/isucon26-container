# シナリオ負荷試験とベンチマーカー

## 公式ベンチを評価の基準にする

競技のベンチは負荷生成、仕様に対する正当性検証、採点とエラーの提示を兼ねる。規約・マニュアルと実装を読み、準備・負荷・事後検証、タイムアウト、負荷の増減、得点タグ・減点・失格条件を把握する。弱い検証の穴を仕様の省略許可と解釈しない。

固定量の試験は、その量を全て処理できる実装同士の差を測れないことがある。競技用の適応的な負荷と、要求レートを固定する容量試験は目的が異なる。補助試験のRPSを公式スコアへ換算しない。

## k6等で補助試験を作る

1. 閲覧・認証・更新・アップロードなどの利用手順と比率、データ分布をモデル化する。全員同じユーザーや同じキーを使って偶然のキャッシュヒットを作らない。乱数の種や入力を記録して再現可能にする。
2. 初期化を一度実行し、完了と事前の正当性確認を待ってから負荷を開始する。準備時間を負荷区間へ混ぜず、固定の開始遅延だけで初期化完了を仮定しない。
3. 仮想ユーザーごとのCookie・セッション・アカウントを管理する。フォームからCSRFトークンを取得し、リダイレクト、multipartのMIMEとファイルサイズ、アップロード後の取得まで実際の契約に合わせる。
4. executor、VU数または到着率、実行時間、読み書きの並行シナリオを明示する。VUの閉ループは遅い応答で要求頻度も落ちる。iterationとHTTPリクエスト数も区別する。
5. ステータスだけでなく本文・更新の反映・権限・並び順をcheckする。失敗をthresholdや終了状態へ反映させ、checkが失敗しても完走した試験を成功扱いしない。
6. 経路別の件数・総時間・分位点・エラーを入口ログと照合する。混合比の変化だけによる平均値の変動、暗黙のリダイレクト、静的リソース取得の欠落を調べる。

ウォームアップと測定区間を分け、監視で挙動を捉えられる時間を確保する。競技では公式の制限時間を守る。本番向けの長時間試験は別途メモリ増加、データ増大、期限切れや再接続を含める。

HTML解析や画像生成などの検証処理が与負荷機を律速し得る。共有する読み取り専用fixtureは活用できるが、k6のSharedArray等をVU間の可変状態共有と取り違えない。書籍の簡略シナリオも公式ベンチの完全な代替にはしない。

## 自作・修正する場合の設計点

- fixture読み込み・初期化、負荷生成、全書き込み完了後の検証を分ける。前段の致命的失敗を後段へ持ち越さない。
- HTTP送信とvalidatorを分離し、本文、Location、認証失敗、静的ファイルや画像のハッシュ、状態遷移を検証する。正常系と意図的な不正入力の両方を用意する。
- 期待値は仕様から作る。並行要求の送信順とサーバーのコミット順が一致することを要求しない。同時更新中の一覧は許される整合性・時刻境界を踏まえて検証する。
- Goでは親contextを伝え、各要求・待機・ループを中断可能にする。WithCancel/Timeoutの解放、全goroutineの終了待ちを行う。一定周期と「処理後に一定間隔待つ」を区別し、select内のbreakだけで外側ループを止めたつもりにならない。
- WaitGroupは起動前にAddし、全経路でDoneする。共有モデル・map・sliceを同期し、使用済みMutexやWaitGroupをコピーしない。単一カウンタにはatomicも候補だが、複数項目の不変条件まで自動的に守られるわけではない。
- fixtureや検証用データは必要量を保持し、大きいバイナリはハッシュ等で検証コストを抑える。想定する最速の実装でも生成・解析・保持が追い付くか確認する。
- 再現に必要な引数、負荷・エラー種別・得点の内訳を記録する。機械可読の結果と診断ログを分け、失敗を終了コードへ反映する。運営用の詳細ログと参加者向け出力の公開範囲も決める。
- 正常な参照実装に加え、更新無視・認証省略・古い固定応答・順序違反等の誤実装を検出できるか試す。ライブラリを使っても仕様固有の検証は実装者の責任となる。
