# DBを律速要因と確認できたとき

## 調査の順番

1. OSからCPU・メモリ・I/Oを観察し、DB内部の実行中クエリ・待ち・接続数と照合する。PROCESSLISTは瞬間の標本なので、頻出だけで総負荷を判断しない。
2. 試行を分離したslow logやPerformance Schemaを集計する。pt-query-digest等で総時間と回数の両方を見て、対象のHTTP経路へ結び付ける。
3. スキーマ、インデックス、データ量と偏り、実行計画を確認し、走査・ソート・転送・ロック・接続確立のどれを減らすか決める。
4. クエリ単体の改善と、正当なシナリオ全体の改善を別々に検証する。

## アクセスするデータを減らす

検索条件と並び順・LIMITを組み合わせてインデックスを設計する。複合キーは列の順序に意味があり、対象クエリでどこまで絞り込めるかを確認する。ソート回避やカバリングが有効か、実行計画と実測で判断する。filesortという語だけからディスクI/Oと断定しない。

InnoDBのセカンダリインデックスから行本体を得るには主キー側の探索が加わる。必要列だけの取得で、巨大な画像/BLOBや不要な文字列の転送・デコードを避ける。カバリングのために大きな列を無差別にキーへ足さない。

インデックスには書き込み・メモリ・保存量のコストがある。重複や不要なキーは使用経路を確認して整理する。全文・空間検索には適した索引を検討できるが、部分一致の意味、トークン化、境界条件、並び順が元の仕様と一致するかを検証する。

想定外の計画はデータの分布・統計・バージョンも調べる。FORCE INDEXや結合順の指定は根拠のある候補として比較する。特定の初期データで速かった計画を、データ増加後も最適と決めつけない。

## N+1を根から減らす

結果件数に比例するDB・キャッシュ・外部APIの往復を探す。候補はJOIN、必要IDを集めた一括取得、リクエスト内の重複排除、共有キャッシュ。最小の構成で呼び出しを減らせる方法から比較する。

- JOINでは欠けた関連、重複行、NULL、フィルタ位置、件数、並び順、ページングの意味を維持する。
- 一括取得では空集合、重複ID、結果の再対応付け、IN句の大きさを扱う。巨大な一括取得はパケット上限・計画・メモリにも影響するので必要に応じて適切な粒度に分ける。
- キャッシュへ移しただけでN回の通信を残さない。multi-get等を使い、未取得キーもまとめてDBから読む。低ヒット率・初回アクセス時も測る。
- ループ内の並列化は往復や仕事量を消さない。接続待ちや下流の飽和を増やす可能性を計測する。

## 接続とI/O

DBハンドルを適切に共有し、プールの待ち時間、利用中/アイドル数、接続の生成・破棄を観測する。全アプリのプロセス数×各プール上限をDB側の上限・メモリと整合させる。接続を増やせば速くなるとは限らない。

PREPARE/CLOSEが支配的なら、ステートメントの再利用やドライバのパラメータ処理方式を調べる。安全なパラメータ束縛を維持し、文字列連結でSQLへ値を埋め込まない。ドライバ固有設定は実装・文字コード・制限を確認して比較する。

読み取りI/Oが支配的なら、作業集合・buffer pool・OSキャッシュ・メモリ圧迫・swapを合わせて調べる。専用DB向けのメモリ比率をアプリ同居サーバーへそのまま適用しない。

更新I/Oが支配的でも、fsync・REDO・binlogの変更前に、競技の永続化条件と復旧要件を確認する。ログを止めたり同期を緩めたりする設定はデータ消失範囲とレプリケーションへの影響を伴う。許容条件が不明なら耐久性を維持したまま仕事量・更新頻度・競合を減らす。

RDBMS/NoSQL/NewSQLという分類だけで性能や整合性を断定しない。置換するなら、対象製品・設定で必要なトランザクション、永続化、読み取りの一貫性と運用コストを満たせることを確認する。
