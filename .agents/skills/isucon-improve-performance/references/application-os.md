# アプリケーションとOSの境界を調べる

## アプリ側の仕事を減らす

- 高頻度の外部コマンド起動は、同等の出力を得られるライブラリへ置き換える候補。起動・シェル・パイプ・メモリのコストを測り、文字コード、改行、バイナリ、ハッシュ形式、失敗時の挙動まで比較する。必要な外部実行ではシェル解釈と引数を区別する。
- 開発モード、DEBUGログ、SQL全件ログ等を確認する。計測用ログは必要な区間だけ有効にし、最終評価時の設定を記録する。障害調査に必要な情報まで失わない。
- 言語名で高速性を決めつけない。JSON、テンプレート、正規表現、メモリ割り当て等の実際のホットパスをプロファイルする。単純な文字列処理で十分かを検討し、出力の安全性を維持する。

## HTTPクライアント

再利用可能なClient/Transportを共有し、要求ごとに接続プールを作らない。応答Bodyは確実に閉じ、再利用に必要な読み切り条件をライブラリ・HTTP版に合わせて確認する。巨大・無限のBodyを無制限に捨て読みしない。

全体期限、接続、TLS、応答ヘッダ等のどの段階をタイムアウトが覆うか確認し、上位要求のキャンセルを伝える。タイムアウトで成功扱いにせず、失敗・再試行・残った処理を観測する。アイドル接続の保存数と、処理中を含む最大接続数は別。各プロセスの設定を合計し、接続先の容量も測る。

## CPU・ネットワーク・ディスクを切り分ける

| 観測 | 次に調べるもの |
| --- | --- |
| user CPUが高い | アプリ・DBのプロファイル、圧縮・TLS・変換、割り当て |
| system CPUやcontext switchが多い | syscall、fork、接続の作り直し、過剰な並行処理 |
| 一部コアやsoftirqへ偏る | 単一スレッド、ロック、NICキュー・割り込みの分散 |
| I/O待ちやディスク遅延 | 読み書き元のプロセス、ログ・一時ファイル、fsync、実デバイス |
| stealやCPU制限 | VM・cgroup・クラウドの制約、与負荷条件への影響 |

平均CPUだけで単一コア飽和を見逃さない。iowaitはCPUが計算をしている割合と同じ意味ではないため、プロセスの待ち・デバイス統計と照合する。straceやeBPFを使うなら対象・時間・負荷への影響を限定する。

ストレージは実デバイス、ネットワーク接続の有無、ファイルシステム、マウント、ブロックサイズを確認する。帯域、IOPS、レイテンシを区別し、逐次/ランダム、read/write、要求サイズ、並列度、ページキャッシュ条件を揃える。fio等は既存データを壊さない専用ファイルで実行する。I/OスケジューラやTRIM方式は、実機の対応とワークロードで判断する。

## 上限に当たったときの手順

1. エラーログと使用量から、FD不足、accept待ち、ローカルポート不足、帯域などの原因を特定する。
2. シェルのulimitだけでなく、実行中PIDの `/proc/<pid>/limits`、systemd、コンテナ、アプリの上限を調べる。必要な上限を見積もるとともにリークや無駄な新規接続を直す。
3. systemdの配布Unitを直接書き換えずdrop-in等で管理する。反映に必要なreload/restartを行い、新PIDの実効値を再確認する。
4. backlogはアプリのlisten値とカーネル側の上限を合わせ、待ち行列・dropを検証する。キューを増やすだけで処理能力は増えない。
5. ephemeral portは接続の再利用を先に確認する。範囲を広げる場合、待受・予約ポートとの衝突と影響範囲を確認する。同一ホストのUnix socketは配置・権限・ライフサイクルが合う場合に比較する。
6. sysctlは現在値・カーネル版・意味を確認し、一時変更と永続設定を区別する。変更後と再起動後の実効値・正当性・性能を検証する。

MTUは端点だけで決まらない。全経路の対応、PMTUD、損失・再送の証拠なしにJumbo Frameへ変更しない。古いチューニング記事の削除済みパラメータや既定値を流用しない。
