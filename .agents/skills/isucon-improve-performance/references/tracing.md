# 分散トレースで因果関係を確認する

## 何を調べるか

経路別のログ集計から、サービス間の待ち、DB・KVSへの反復呼び出し、業務処理の内訳が不明なときに使う。Trace IDで要求全体、Span IDと親子関係で処理のつながりを確認する。長いスパンはCPU処理とは限らず、接続・ロック・下流応答待ちも含む。

ウォーターフォールでクリティカルパスと反復回数を見る。親と子の時間、並列に重なる時間を単純加算しない。遅い1件だけを全体の代表にせず、入力・経路・遅延帯を変えてログ集計と照合する。

## 最小限の計装

1. 対象言語・版で使えるOpenTelemetryのAPI、SDK、計装ライブラリを確認する。HTTPサーバー・クライアント・SQLの既存計装を基本にし、未知の業務処理へ手動スパンを足す。
2. 起動時にサービスを識別するResource、Provider、Exporter、バッチ送信を構成する。送信先・プロトコル・ポートを実環境に合わせ、終了時のフラッシュに期限を設ける。
3. スパン開始後に返ったcontextを下流のHTTP・SQL処理まで渡す。受信側で伝播情報を抽出し、送信側で注入する。W3C Trace Context等のpropagatorを両側で揃える。無関係なBackground contextを途中で作って親を切らない。
4. 全終了経路でスパンを閉じる。エラー記録とステータスを設定し、メソッド・正規化した経路・クエリテンプレートなど必要な属性を残す。
5. 実際の要求を流し、同じTrace IDの下に期待するHTTP・業務・DBスパンが正しい親子関係で並ぶことを確認する。収集できただけで伝播成功としない。

GoならHTTPハンドラ/TransportやSQLドライバのラッパーが候補。自動計装で業務処理まで全て見えるとは仮定せず、二重計装も避ける。Jaeger等の可視化基盤とアプリへの計装は別に検証する。

## 運用と測定への影響

- ログにtrace_id、必要ならspan_idを付け、同じ要求の詳細へ移動できるようにする。
- 全件収集はCPU・メモリ・転送・保存量を増やす。サンプリング率と送信キューを定め、計装あり/なしの性能差を確認する。細かいオンメモリ処理への大量スパンは特に注意する。
- head samplingは開始時に選別するため稀な失敗を取り逃し得る。tail samplingは完了結果で選べるが、判断までの保持コスト・遅延と、同一トレースを同じCollectorへ届ける設計が要る。目的とコストに合わせて選ぶ。
- 認証情報、Cookie、個人情報、SQLパラメータの生値を無条件に記録しない。必要最小限の属性・マスク・保存期間を決める。
- 最終比較では計装条件を揃える。調査用設定の撤去だけの効果と、対象処理の改善効果を分けて報告する。
