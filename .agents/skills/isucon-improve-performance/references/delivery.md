# リバースプロキシと配信経路

## 役割と適用範囲を確認する

アプリの処理モデルと、遅いクライアントが占有する資源を調べる。nginx等への静的配信・TLS・圧縮・バッファの移管は、アプリの仕事を減らせる場合に選ぶ。各ホップのCPU・帯域・接続・一時ファイルを比較する。

設定は実際のバージョン、組み込み機能、有効なinclude、locationの優先順位を調べて編集する。構文検査、reload、実際の応答の確認まで行う。書籍のバージョンの既定値を対象環境へ持ち込まない。

## 圧縮とバッファ

- 圧縮は転送量とCPUの交換。Accept-EncodingとContent-Encoding、対象MIME、最小サイズを確認する。既に圧縮された画像や小さい応答を無差別に圧縮しない。方式・レベルは実クライアントの対応と全体の計測で選ぶ。
- 静的な事前圧縮を使うなら、元ファイルとの同期、非対応クライアント、キャッシュの表現別管理を検証する。
- request bodyとupstream responseのバッファは別々に見る。大きなデータが一時ディスクへ流れる条件、容量、I/O、メモリ予算を確認する。tmpfsへの移動もメモリ消費を測る。
- バッファが遅いクライアントからアプリを解放する効果と、ストリーミングを遅らせる効果を区別する。SSE等は対象経路ごとにflushを検証する。

## 接続とプロトコル

- クライアント側とupstream側のkeepaliveを区別する。接続の新規生成、TCP状態、エラーログ、プール待ちを調べる。keepaliveのキャッシュ数を総接続数の上限と誤認しない。
- HTTP/2・HTTP/3は、実際の経路・対応・RTT・損失・並行要求で比較する。HTTP/2の多重化だけでTCPの待ちが消えるわけではない。TLSの暗号化や証明書検証を弱めて性能を作らない。
- TLSセッション再開やkTLS等はOS・ライブラリ・構成の対応を確認する。0-RTTは再送攻撃への性質を理解せず書き込み要求に有効化しない。
- Early Hintsは、実ブラウザでクリティカルな資源の取得開始が早まる場合に検討する。最終応答も必要。不要な先読み・帯域競合を確認し、サーバーのベンチスコアへの効果とは分ける。

## ファイル配信

sendfile等のコピー削減は対象ファイルシステムと配信経路で測る。open_file_cache等はFD・メタデータの再利用と更新反映の交換であり、アップロード直後・置換・削除・存在しなかったファイルの出現も検証する。

DB内の画像等をファイルへ移す場合、初期化・新規アップロード・複数台での共有・更新・削除の経路も実装する。MIME、認可、URLと内容の対応を維持する。認可が必要ならアプリで確認してから内部配信へ委譲する方法を検討し、直接URLで認可を迂回できないか確認する。

## HTTPキャッシュ

- freshness内で通信を省くキャッシュと、条件付き要求で304を返し本文転送だけを省く再検証を区別する。ベンチマーカーが実装する範囲も確認する。
- Cache-Control、ETag、Last-Modifiedを実応答で確認する。複数台で同じ内容に異なるvalidatorが付かないか、変更された内容が同じvalidatorを持たないかを調べる。
- 長期間キャッシュする資源は内容の版とURLを対応させる。クエリ文字列を版に使うなら、各層のキャッシュキーに含まれるか確認し、変更時だけ版を変える。混在デプロイで旧内容を新版のキーに保存しない。
- 共有キャッシュのキー、認証・Cookie・Set-Cookie、Vary、private/no-store等の実装を確認する。ヘッダを無視して個人別応答を共有させない。別ユーザー・権限・圧縮表現・クエリ・更新後で検証する。
- CDNやオブジェクトストレージは競技で利用が許可される場合に限る。MIME、圧縮、TTL、削除反映、オリジン負荷、障害時の挙動を各サービスの現行仕様で確認する。
