# 改善を積み重ねるときの判断

付録Aのprivate-isu実践から一般化した判断手順。そこでのハードウェア、点数、パラメータ、改善順を別の問題の目標や処方箋にしない。

| 観測 | 次の判断 | 改善後の証拠 |
| --- | --- | --- |
| DBがCPUを占有し、多数行を走査 | SQLと条件に合う索引を確認 | 選択キー、走査量、DB負荷と全体の処理量 |
| 画像や静的ファイルが高頻度でアプリを通る | 配信責務と保存方式を見直す | 初回・更新後・初期化後の内容、アプリ/DB転送量 |
| 全行取得後にアプリで絞り込み・打ち切り | フィルタ・JOIN・LIMITをDBへ移す | 削除済みデータ、欠けた関連、件数と並び順 |
| 単発は速いSQLが大量発行 | トレースで発行箇所を探し、往復を削る | 要求あたりの呼び出し回数、総時間 |
| DBからKVSへ移したが逐次Getが残る | multi-get等でまとめる | 冷えた状態のDB負荷も含めた待ち時間 |
| 外部コマンド・接続確立が頻発 | ライブラリ・接続再利用を比較 | 出力の同等性、新規接続数、プール待ち |
| 与負荷側に資源上限のエラー | ベンチ機の実効上限と消費を調べる | 実プロセスの上限、エラー解消、与負荷の余裕 |

新しいインデックスが他のクエリの実行計画を悪化させることもある。追加直後のスコア低下を見逃さず、関連する全経路の計画・負荷を確認する。ヒントを使う場合も入力分布とデータ増加への依存を把握する。

初期に追加した索引や処理削減は、後続の改善を支える前提になり得る。最終状態で負荷が小さいからといって、証拠なしにその最適化を取り除かない。削除や設定整理は単独変更として正当性と全体性能を再検証する。

DBの余裕が生まれ、アプリやプロキシへ律速が移ったら、その層を再調査する。スケールアウトを選ぶ場合は、セッション・ファイル・キャッシュ・接続予算・書き込み整合性を確認する。負荷を減らせる設計と、資源を増やす判断を全体の費用と運用条件で比較する。
